# PP-106 opt-in external data and compute broker

Research/design only, 28 October 2026. The first action was fetching [issue 61, PP-106](https://github.com/ManuelR-T/paperplay/issues/61). Its size is **discovery**, explicitly timeboxing a prototype/design before implementation estimates. Scope: reviewed data/compute adapters with source/asset selection, upload disclosure, budgets, job lifecycle and returned evidence; provide **local-file and deterministic fake remote adapters first**. Dependencies: PP082/083/085/094/099. No application, ledger, provisioning, credential, paid call or held-out corpus change is made here.

**Recommendation:** implement one small broker module with two registered adapters: browser-only checked-file import and a clearly labeled fake job behind same-origin application routes. Ship no real external dataset downloader, GPU provider, credential picker, arbitrary URL, shell/container command or uploaded model code in this discovery slice. The fake must exercise durable ownership, reservations, ambiguous submission, resume/cancel and identity checks; its output is engineering simulation evidence, never a heavy-compute or scientific-reproduction claim. This meets the issue's requested first adapters without deploying infrastructure.

## Minimal contract proposal

All records are strict, versioned, bounded inert JSON. Suggested names are proposals, not existing exports.

- **`BrokerRequirement`**: kind `dataset | weights | compute`; source fingerprint/anchor IDs; human meaning; expected artifact/version/digest/bytes when known; local availability; named missing details; optional registered adapter reference. Unknown identity is explicit, not silently accepted as a compatible weight version.
- **`BrokerAdapterDescriptor`**: trusted ID+version; local/fake/remote classification; supported requirement/input/output kinds; fixed recipient label; privacy/retention statement; resource units/ceilings; capabilities for idempotency lookup, retrieval, cancellation and deletion. Public metadata is not executable configuration. Endpoint/credentials are application-owned server configuration, never fields selected by a model or manifest.
- **`BrokerRunRequest`**: UUID run ID; exact adapter/version; source fingerprint; selected asset IDs, manifest checksums and raw serialized-byte SHA-256/length; named parameter/version/seed values; immutable per-run budget; consent/disclosure version and digest. Include only explicitly selected input projection, not the entire paper, every local attachment or a hidden conversation context. Selected manifests may already contain source excerpts and derived private values: disclose those too.
- **`BrokerBudget`**: maximum creations (one in the MVP), input/output bytes, elapsed deadline, status/download requests and resource counters; money is integer minor units plus currency where actually enforceable. Fake/local cost is explicitly zero; future real adapters must document what is hard-enforced by provider versus estimated by Paperplay. Unknown price or unenforceable compute ceiling blocks real paid admission rather than becoming “free.”
- **`BrokerJobRecord`**: owner, run/request digest, reservation ID, state/revision, accepted opaque provider reference if any, durable cancellation request, deadlines, lease owner/expiry/fencing generation, bounded measured/reserved resource metadata and result digest. Private input bytes are not casually logged in the ledger. Metadata-only persistence cannot reconstruct missing input: reattach identical selected bytes and verify the hash, or report a recoverable missing-data condition.
- **`BrokerResultEnvelope`**: exact request/adapter/job binding, input hashes, model/weights/data versions if relevant, declared output media/schema/bytes/hash, provenance/rights, provider resource measurements with “unavailable” distinct from zero, and evidence category. A provider saying completed is not a validated output or an independent scientific check.

Suggested deep interface: `prepare(selection,budget)` creates the immutable disclosure/quote without provider submission; `start(preparedRun,explicitConsent,selectedPayload)` atomically claims that run; `status(jobRef)` only retrieves; `cancel(jobRef)` durably requests cancellation; `collect(jobRef)` downloads a bounded accepted result. A future `reconcile(jobRef)` may look up an existing submission by provider idempotency key; it cannot authorize new work. Transport retry of the **same** idempotent run is different from authorizing a new run. Modified inputs/adapter/budget require a new disclosure and explicit action.

## Consent, privacy and bounds

The user-visible review names recipient, selected sources/assets, included excerpts, exact serialized bytes, purpose, maximum cost/resources, retention/deletion terms and limitations of cancellation. Default upload selection is empty. File import, variable edits, scrubbing, local render, polling a stored local snapshot, reopening and generated SDK events never imply upload consent. An explicit start authorizes only its frozen run; it is not a persistent “allow all paper data” toggle.

Local-file adapter: browser file selection → bounded format validation → existing source-bound asset checks → local binding. No network, job quota or external consent pretense. Known missing weights can be named even when this adapter cannot execute them. Fake remote adapter: explicitly disclose that selected payload goes only to this application's server and that **no external provider is contacted**. Its deterministic identity/echo fixture does not pretend to run on scientific data: server checks bounded payload/hash and returns inert engineering output; final scientific asset admission happens locally against the exact source. Do not require uploading the whole source PDF merely to echo a selected asset. If original source context is necessary for a later real adapter, disclose and select it explicitly.

Proposed discovery ceilings, requiring implementation measurement: ≤2 MiB selected input and ≤2 MiB collected output, one creation/run, one active job/browser, ≤5-minute run deadline, bounded status calls (e.g. ≤60 with backoff), ≤30-second individual handler wait. Stream-count actual bodies; `Content-Length` and user-declared size alone do not enforce the ceiling. Cap parsed structure and decompressed bytes separately; initial fake accepts no archives. Do not keep a Next request open for the entire heavy computation. Accepted-job inspection/cancellation must remain available when new-creation quotas are exhausted; polling/download accounting is separate from creation quota.

No adapter accepts arbitrary outbound URLs. Future real adapters use exact reviewed endpoint IDs, validate provider-returned download locations under that same policy, reject redirects unless independently validated at every hop, restrict DNS/IP destinations and credentials, and apply egress restrictions. CORS is not server-side authorization or SSRF prevention. [OWASP's primary SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html), identified/trusted-application case, recommends allowlisting and disabling automatic redirects. This is a future adapter-admission requirement, not a claim that the current app has a general safe downloader.

## Durable submission, leases and cancellation

Use a monotone state machine: `prepared → reserved/submitting → accepted/queued/running → completed | failed | cancelled | expired`, with explicit **`uncertain`** and **`cancel-requested`** states that do not masquerade as terminal completion. Keep provider raw status separate from normalized broker state and record a status revision. Terminal output identity cannot change on a late poll; measured spend cannot decrease just because a stale response arrives. Locally expiring tracking does not prove a running provider job stopped or became free.

Commit owner+request hash+reservation+submission claim before calling a provider. A lost response after acceptance is the crucial boundary: if the provider can retrieve by the same idempotency key, reconcile; if it cannot, retain uncertainty and reservation and do not submit a replacement. [HTTP RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) does not authorize blindly retrying non-idempotent POST operations. Provider idempotency has its own retention/parameter rules: for example, [Stripe API v1 documentation](https://docs.stripe.com/api/idempotent_requests) describes replaying stored responses (including 500s), parameter comparison and key pruning after at least 24 hours. That is evidence that such guarantees are provider-specific, not a proposal to integrate Stripe or assume the same behavior from compute services.

A lease coordinates a worker's reconciliation/polling ownership; it is not permission to recreate the paid job. Use atomic compare-and-swap with a fencing generation for durable mutations; a stale holder cannot settle a newer lease's record. An expired lease after ambiguous creation goes to retrieval/uncertainty, never a new creation attempt. [AWS SQS visibility-timeout documentation](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html) explicitly says visibility does not guarantee against duplicate delivery. Therefore neither a queue nor a timeout alone establishes exactly-once provider side effects. No queue installation is needed for the deterministic fake; a durable job store plus injected clock can exercise these semantics.

Distinguish **stop local polling**, **request provider cancellation**, **provider-confirmed stopped**, and **delete retained inputs/results**. Aborting a browser request is not a remote rollback: [WHATWG Fetch abort algorithms](https://fetch.spec.whatwg.org/#abort-fetch) cancel local fetch/body processing, not an application-specific compute job. Concrete provider counterexample: [AWS Batch CancelJob](https://docs.aws.amazon.com/batch/latest/APIReference/API_CancelJob.html) may return success while a STARTING/RUNNING job is not cancelled; those jobs require [TerminateJob](https://docs.aws.amazon.com/batch/latest/APIReference/API_TerminateJob.html). Providers may still charge work already performed. Keep cancellation requested until reconciled; concurrent completion can win with a validated result and truthful cost. A late cancellation response cannot erase an already accepted immutable result.

## Returned identity, evidence and generated-code boundary

Before installation, verify exact adapter/version, job/run/request digest, source fingerprint, selected input hashes, declared model/weights/seed parameters, output size, raw-byte digest, parsed schema and existing ScientificAsset checksum/source owner. Preserve raw bytes on unsupported versions or validation failure for explicit recovery; retain the last accepted local result. Remote result origin is externally computed/reported, not observed unless the admitted source actually supplies observations. A fake result is illustrative engineering output. Provider logs, score claims or a digest cannot mint an experiment-reproduction receipt.

[RFC 9530](https://www.rfc-editor.org/rfc/rfc9530.html), §§2–3 and 6, distinguishes content/representation digests and their security limits; a hash detects a mismatch against a trusted expected value, but a server returning both arbitrary data and its hash does not establish scientific authenticity. Specify whether the broker hashes raw serialized bytes, decoded content or a canonical manifest. Do not confuse the existing manifest checksum with a transport-byte SHA-256 or trust ETag as that checksum.

Generated artifacts retain their current capped QuickJS/data-only SDK path. Do not add a broker host callback, SDK control command, URL fetch, credential handle or permission flag to generated code. A generated artifact may declare a named missing requirement as inert metadata, but only trusted application UI can prepare and start an approved adapter. Broker consent/session tokens never enter guest inputs/state/frames or portable bundles. This is an application boundary to test, not a claim of complete browser/process isolation.

## Discovery verification and decisive exit criteria

Use project-authored tiny inputs and an injected fake adapter/clock/store; no held-out corpus, real provider or paid CI:

1. Local file meets an exact requirement; missing dataset/weights/compute are named with original version/digest, without silently substituting an unrelated engine. Oversized requirements keep a useful conceptual fallback.
2. Mount/filter/render/import/reopen do not call `start`, upload bytes or invoke a provider. Review disclosure changes when selection, source excerpt, bytes, budget or adapter changes; stale consent fails. Generated SDK events have no broker path.
3. Duplicate starts, concurrent processes and response-loss injection create at most one fake provider job for the exact run. Changed request under the same ID fails. Crash before submission, after provider acceptance but before reference persistence, and after reference persistence each have explicit recovery behavior. Unknown acceptance never causes replacement.
4. Lease expiry/fencing, stale polls, provider-status regression and cancel-versus-complete races preserve identity and conservative resource charges. New work is blocked on unavailable durable admission; accepted-job retrieval/cancel does not depend on creation enabled or new quota remaining.
5. Enforce streamed input/output bytes, parsed limits, poll/deadline/resource budgets and unsupported-result recovery. Wrong input/source/model/seed/result hash is rejected. Imported declarations do not restore integrity/compiler/scientific receipts. Portable export excludes live owner/provider credentials by construction.
6. Native-browser walkthrough: choose local input, see named unmet requirement, review fake-recipient disclosure, explicitly start, close/reopen, resume the same accepted job, cancel or collect, and inspect verified identity plus unverified evidence label. Offline/rejected/incompatible states retain local reading and the prior result. No claim of actual heavy compute, deployment or human reader study.

Discovery is complete when this local+fake contract and failure harness satisfy the four issue criteria. A real provider is a separate admission: primary documentation for its idempotency horizon/lookup, cancellation, retention/data use, enforceable costs/resource ceilings, allowed endpoints and result formats; reviewed credentials/egress; shared durable deployment support. Railway provisioning, releases and real trained-weight execution remain separate work. No dependency or real-provider account is justified by this MVP.
