# Bounded Muse context and budget accounting

PP-111 replaces the growing all-widget prompt in the section enrichment and generated-artifact paths with deterministic, source-bound selection. The original fixed six-engine M2 analysis path remains compatible; it does not receive the growing SDK recipe catalog.

## Selection and authority

`lib/retrieval/selection.ts` admits at most three capability descriptors, two examples and 24 KiB of retrieved content. Its query binds the selected context, source fingerprint, section, purpose and any exact target/required versions. The small common manifest lists available identities and denied guest privileges. Lexical ranking bounds prompt size; it does not prove scientific applicability.

Unknown explicitly required identities, formats and exact versions return a blocking gap. A section without a specialized lexical match may receive an informational conceptual-diagram fallback. This grants neither a scientific solver nor an external package. Returned declarative widget kinds must belong to the admitted selection. Generated SDK calls receive a separate method-admission check before the existing compiler, isolated runtime and quality checks. A selection receipt is not a compilation or scientific-verification receipt.

The catalog includes actual source-coded recipes tested through Acorn and QuickJS initialization and slider endpoints. The SDK source is sent once, separately from the selected examples; selected custom-runtime grammar retains its required semantics without repeating example bodies.

## Paid creation and local use

The workbenches show the locally selected context and ceilings before the existing explicit creation action. Generation freezes one selection for the reviewed run, including its repairs, with at most three attempts. Sliders, seeking, previews, local checks, reopening and retrieving an existing job do not create inference requests.

Server admission recomputes current selection for new creation and retains compact frozen metadata for accepted-job recovery. Generation also pins SDK and prompt-contract hashes. A changed contract requires a new reviewed run rather than silently repairing under different rules. Old receiptless jobs remain retrievable/cancellable, including after SQLite reopening; starting a new repair from such a run requires a fresh reviewed run. Existing request identities, uncertain-creation policy, cancellation and paper/global quota reservations remain authoritative.

Durable metadata contains selection/example hashes and versions, exact serialized-request SHA-256 and request measurements. It excludes source/context bodies, example bodies, credentials and bearer job capabilities. Recovery validates saved metadata without requiring the current catalog to match an earlier accepted request.

## Measurements

Pure provider request builders count the complete serialized body: fixed instructions, selected input, output JSON schema, included feedback, model identity and request options. Diagnostic component counts are not charged a second time. UTF-8 bytes plus 256 is a labeled input-token estimate. The existing conservative quota reservation remains `serializedCharacters * 4 + 16000 + maxOutputTokens`. Neither value is measured provider usage or a financial quote. Provider-reported usage is recorded separately; unknown is `null`, not zero.

Run the offline development report with:

```sh
npx tsx scripts/report-retrieval-payloads.ts data/retrieval-payload-development.json
```

The report records all twelve frozen corpus members. Eight development entries have serialized measurements: C1/C2 use existing saved excerpts, B1 uses an existing short attribution/caption card, and five use explicitly labeled intake metadata only. These are not full-paper coverage measurements. Across those eight contexts, planning bodies are 9,803–26,028 bytes, saving 7,990–24,777 bytes against a counterfactual that swaps only the selected input for the broad catalog while keeping current instructions/schema/model fixed. This counterfactual was never submitted. Generation still needs the common SDK, so retrieval does not promise every generated prompt becomes smaller.

The four held-out entries deliberately retain null payload and usage until PP-113 freezes implementation, catalog and prompts before source admission. PP-111's frozen-corpus measurement acceptance remains pending that evaluation. Every case also records an explicitly synthetic unavailable-capability probe; it blocks before creation. The report and its fetch-denial test make zero inference calls. Offline measurements use a declared model-name placeholder; production accounting uses the actual configured request body.

## Verification limits

The implementation checkpoint passes TypeScript, 706 automated tests and the production build. Tests include all bounded widget triples, executable SDK examples, malformed/stale selections, full-request accounting, provider admission, deduplication, frozen repairs and receiptless SQLite recovery. Browser fake-provider evidence, when recorded, tests the real interface and local workers against authored responses; it is not a live Muse quality evaluation or measured Meta usage. Human usefulness and scientific validity remain separate checks.

Native Chromium evidence: `data/retrieval-browser-ui.json` and desktop/mobile screenshots record one fake planning call and two fake generated attempts. The first authored scene failed actual local quality checks; the second passed. The same selection hash survived repair, local recheck/Add/Remove/reopening added zero creates, and 320 px layout retained 44 px buttons without horizontal overflow. External inference calls were zero. An initial cross-port test-harness header error was corrected only in the temporary proxy and is retained in the report.
