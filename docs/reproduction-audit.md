# Original-experiment audit and restricted replay — PP-039

Checked 27 October 2026. **One deterministic original merge-cost subexperiment was replayed using the author's code. The complete hardware running-time study was not reproduced.** This evidence does not upgrade a browser TypeScript engine to an original-experiment reproduction label.

## Primary evidence and pinned artifact

The [publisher paper](https://doi.org/10.4230/LIPIcs.ESA.2018.63) points to supplementary code DOI `10.5281/zenodo.1241162`. The author's [publication page](https://www.wild-inter.net/publications/munro-wild-2018) links the implementation. The extended paper's [§4.4 / Figure 5 and Appendix C](https://arxiv.org/html/1805.04154v1#S4.SS4) describe the Timsort-drag inputs, merge-cost normalization and original environment.

The original repository's `paper` tag resolves to **`4418605e48a9598a7980e4c432ecc79cf11a38e1`**. This was verified with `git ls-remote --tags https://github.com/sebawild/nearly-optimal-mergesort-code.git` and by checking out that exact commit. Use the [pinned paper artifact](https://github.com/sebawild/nearly-optimal-mergesort-code/tree/4418605e48a9598a7980e4c432ecc79cf11a38e1), not an evolving default branch. The newer author-linked `sebawild2` mirror had later fixes and no tags, so it was not used for the replay. Zenodo HTTP access returned 403 during this audit; the original Git tag remained accessible.

The downloaded author source is MIT-licensed, copyright Sebastian Wild (2018). It was cloned to a temporary directory for execution, not vendored into Paperplay. The committed bounded driver calls the author's public classes without copying their algorithms. Bundled publisher paper attribution remains separate from this software license.

## Replayed original subexperiment

The replay uses the original author implementation and input generator for the merge-cost part of Figure 5:

| Setting | Value |
| --- | --- |
| Input size | `2^24 = 16,777,216` integers |
| Input family | Author `Inputs.timsortDragGenerator(32)` |
| Seed | `248442268`, from the author's experiment script |
| Run-length scaling | 32 |
| Algorithms | Author Powersort, Peeksort, top-down mergesort (cutoff24), instrumented Timsort merge-policy variant `TimsortTrot` |
| Samples | Three generated inputs per method; first excluded, two retained |
| Metric | Author `MergesAndRuns.totalMergeCosts`: sum of lengths of merged runs |
| Validity check | Every one of twelve outputs checked sorted with the author's `Util.isSorted` |
| Execution bound | One allowed CPU core, JVM heap capped at 512 MiB |

The author code was compiled with the installed OpenJDK21 compiler using source/target8 and then run with assertions. The compiler warned that the original Java8 bootstrap class path was not present; this is not the original Oracle8 toolchain. Hardware was an Intel Core Ultra9 285H on Linux, rather than the paper's 2018 machine. No wall-clock sort time was interpreted or reported.

[Actual machine-readable observations](reproduction-merge-cost.json) contain all twelve counts, source commit, driver hash, Java/OS/CPU identification, parameters and the comparison boundary. Raw counts were captured from the actual process, not generated by Meta.

| Author method | Mean merge cost over retained inputs |
| --- | ---: |
| Powersort | 301,730,336 |
| Peeksort | 311,256,766 |
| Top-down mergesort | 322,318,080 |
| TimsortTrot | 419,432,256 |

TimsortTrot's measured merge-cost overhead relative to top-down was **30.1299%**, consistent with the paper's approximately30% merge-cost statement for these inputs. Powersort's merge cost was approximately93.61% of top-down's. These are operation-model comparisons, not speedups, seconds, hardware benchmarks or claims about arbitrary inputs.

The comparison uses a qualitative25–35% interval corresponding to rounding to the paper's ten-percentage-point wording. It was not preregistered, is not a confidence interval, and does not establish equality to the original unpublished CSV averages. We report this as a **restricted deterministic replay consistent with the original qualitative merge-cost finding**, not replication of every Figure5 value or of its running-time chart.

## Repeat the bounded replay

Requires Git, Linux `taskset`, and a JDK with its compiler module; no Meta credential or inference is used:

```sh
npx tsx scripts/reproduce-merge-cost.ts          # explanation only
npx tsx scripts/reproduce-merge-cost.ts --run    # explicit download + bounded execution
```

The script downloads the exact original tag commit, compiles unmodified author source plus `scripts/fixtures/BoundedFigure5.java`, and writes a fresh `docs/reproduction-merge-cost.json`. It caps the Java process at240 seconds and512 MiB and refuses an unexpected artifact commit or incomplete/sortedness checks. This is deliberately excluded from routine CI and browser rendering.

## Complete runtime study: not reproduced

The original [experiment script](https://github.com/sebawild/nearly-optimal-mergesort-code/blob/4418605e48a9598a7980e4c432ecc79cf11a38e1/paper-experiments.sh) includes much larger repetition counts, random permutations up to100million items, a random-run experiment and the full Timsort-drag study. Its harness includes a12,000-round warmup and discards the first measured sample. The paper's environment uses Oracle Java8u161, a particular Intel i7 machine and controlled execution; it does not match this current host.

Recreating those hardware/runtime results would require the exact original environment or a separately justified cross-platform replication design, larger sampling, archived reference measurements and an appropriate comparison tolerance. Executing a reduced Java or JavaScript timing loop on this host would not supply that evidence. No such runtime success is claimed and no full benchmark suite was run.

## Browser scientific labels remain bounded

Paperplay's TypeScript Powersort uses its separately checked merge-scheduling mechanism with simplified buffering and no original runtime optimizations. The Java replay above executes different code and much larger inputs than the teaching UI. It cannot be used as evidence that the browser reproduced the author's full experiment. Prepared browser labels therefore remain mechanism/simplified illustrations; unsupported or model-selected figures do not self-certify scientific reproduction.
